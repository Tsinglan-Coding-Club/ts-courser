# 功能补充判断

日期：2026-09-05。依据：当前工作区的模型、路由、视图和学习/教师模板，包括未提交变更。本文是产品建议，不是已确认的开发任务，也不表示下述功能已实现。范围限于校内教学功能；部署、安全加固、框架升级不在此排序中。

## 判断

项目已经具有课程内容、测验、Python 练习和教师查看提交的基础能力。下一阶段最有价值的是补齐日常教学流程：教师能布置任务，学生知道该做什么，双方能保留每次提交和反馈，并完成订正。

现有“完成率”来自已读课时数量；提交测验或代码也会自动标记已读。因此它能说明学习活动，不能独立说明学生是否掌握内容。下一步应明确区分“看过、交过、通过、已订正”。

## 建议优先级

| 优先级 | 补充功能 | 当前缺口 | 第一版可交付范围 |
| --- | --- | --- | --- |
| P1 | 提交历史与独立草稿 | 测验和代码都只有一条当前记录；代码重新 Upload 会清除正式提交状态 | 草稿与正式提交分开；每次提交保留快照、时间和对应反馈；显示版本列表 |
| P1 | 教师反馈与订正 | FRQ 只有对/错；代码可查看源码和测试结果，缺少持久化教师反馈 | 整份作业评语、需订正/通过状态、学生重交、教师复核；FRQ 增加分值和部分得分 |
| P1 | 作业布置与学生待办 | 目前课时即内容入口，没有独立任务、截止时间或跨课程作业清单 | 教师选择课时布置作业并设截止时间；学生查看未交、已交、待订正；教师查看缺交/迟交 |
| P2 | 教学班与学期 | 只有逐课程报名；没有可复用班级和学期组织 | 班级名单、批量分配课程/作业、按班查看提交、学期归档；与既有账号方案统一 |
| P2 | 成绩册与题目分析 | 有阅读进度和逐份批改，没有统一成绩视图 | 学生×作业表格、未交/待批/得分区分、CSV 导出、逐题正确率与常见错误 |
| P2 | 内容复用与发布版本 | 课程和课时直接编辑，缺少复制/版本模型 | 复制课程、章节、课时；复制时不带学生数据；发布内容与编辑草稿分开；提交绑定题目版本 |
| P3 | 课时提问与学习笔记 | 缺少与具体教材/题目关联的交流记录 | 学生提问、教师答复、已解决标记、个人笔记和书签 |
| P3 | 错题复习与针对性练习 | 有单次结果，没有跨测验复习入口 | 已发布结果中的错题集合、重练、教师解析、基础知识点标签 |

P1 适合下一轮开发；P2 应根据真实班级使用频率逐项推进；P3 可在提交和反馈流程稳定后再做。上表是价值排序，具体开发时“题目版本快照”应随提交历史一起完成，不必等到完整内容版本管理。

## 最值得先做：提交、反馈、订正

一个具体场景：学生提交第一版程序，教师指出边界条件问题；学生保存第二版草稿时，教师仍然能看到第一版及自己的反馈；第二版正式提交后，双方可以比较改动，教师将它标记为通过。

目前 `CodeSubmission` 把草稿上传和正式提交放在同一条记录中，不能完整表达这个过程。`QuizSubmission` 同样覆盖当前答案；旧人工评分被清除是正确的一致性处理，但学生的学习过程也随之不可追溯。

第一版验收应包括：

- 新草稿不覆盖已经提交的作品；一次正式提交产生一个可回看的版本。
- 教师评论和评分绑定具体版本，学生修改后旧反馈仍然保留。
- 学生可看到“待批改、需订正、已通过”及反馈；教师能筛选等待复核的作业。
- 测验提交保留题目、选项和评分依据快照，教师改题后仍能正确查看旧答卷。
- 明确历史数据没有旧版本可还原；接入时将现存记录作为起始版本，不虚构历史。

首版不必做逐行代码评论、复杂评分量表或自动评语。整份作品评语加版本记录，已经能满足大量课堂反馈需求。

## 作业布置：把课程内容和教学任务分开

同一个课时可能由不同班级在不同日期完成。建议让“作业”引用课时，同时保存布置对象、发布时间、截止时间和重交规则，不直接把所有安排写死在 Episode 上。

班级功能尚未完成时，可以先向当前课程的学生布置作业，但应明确名单规则：保存布置时的名单快照，还是让以后加入的学生也自动收到作业。首版建议保存名单，并提供补发入口，避免教师看到的缺交人数随报名变化。

学生需要一个跨课程的“我的任务”入口：先显示需订正和即将到期，再显示其他未完成任务；已经提交但尚未批改的作业应有独立状态。教师则需要缺交名单、批改队列和站内发布反馈通知。邮件或 Teams 推送可后续接入。

截止时间也应区分“标记迟交”和“禁止提交”。校内练习第一版建议允许迟交并标记，不让截止时间直接切断学生补交与订正。

## 成绩与进度：先定义含义，再增加图表

保留现有阅读进度，同时增加独立的提交状态和成绩。未交、待批、错误答案、零分不是同一个状态；FRQ 未批完时应显示待完成评分，而不是给出误导性的总成绩。

成绩册第一版选择明确、简单的规则，例如每题配置分值，显示已得分/总分和评分完成状态。若允许多次提交，应由作业规则确定采用最新、最高还是教师指定成绩。题目分析沿用同一选取规则，并显示参与人数；尚未完成人工评分的题目不混入已评分正确率。

代码测试通过情况可以继续用于练习反馈。是否正式评定为通过，应有教师确认入口，不必为了实现基础反馈流程先建设独立服务端判题系统。

## 其他有价值但不宜抢先的功能

- **教师预览未发布课程**：当前学习视图要求课程已发布，教师不能直接按学生布局预览未发布内容。这是范围较小、能改善备课的补充，可穿插优先完成。
- **课程/课时搜索**：当前课程列表主要按标签筛选；当课程或课时数量增加后，标题和内容关键词搜索会比推荐算法更直接。
- **文件作业**：如果非编程学科使用增加，可支持学生上传图片/PDF、教师反馈，补足当前 Paper 主要用于阅读的能力。
- **学习路径和先修要求**：适用于连续编程课程，但应先定义通过条件，并保留教师解锁能力。

暂时不优先建设课程评分商城、公开社交广场、积分排行榜或通用 AI 助教。它们可能有价值，但与当前校内课堂的提交、批改、补交需求相比，尚无足够的仓库证据支持把它们排在前面。

## 与现有计划的关系

[账号升级方案](ACCOUNT_SYSTEM_UPGRADE_PLAN.md)与[管理员发号规格](ACCOUNT_ADMIN_UI_SPEC.md)已经覆盖 Microsoft 登录、校内账号发放等方向，不能当作尚未考虑的新创意，也不能当作已完成能力。班级管理应与它们共用学生身份和班级概念，避免单独再建一套名单。

建议的落地顺序：提交版本与题目快照 → 教师反馈/订正 → 作业与待办 → 班级/成绩册 → 内容复用和复习工具。小范围的未发布预览、课程复制可以根据教师反馈穿插。
