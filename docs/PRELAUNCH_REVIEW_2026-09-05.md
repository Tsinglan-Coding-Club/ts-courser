## 必须优先处理的发现

### R1 · P1：公开注册可创建业务管理员

位置：`accounts/views.py:65,104-108`；`accounts/models.py` 的 `is_admin`；`teacher/decorators.py`。

注册请求中的 `role` 被原样写入数据库。模型的 choices 不会在 `create_user()` 时自动构成校验；`role=admin` 会让 `is_admin` 为真，绕过教师审核与课程所有权检查。

复现：在测试 session 中准备有效邮箱验证码，POST 注册并传入 `role=admin`，返回 302；新用户 `is_admin=True`，访问另一教师的课程编辑页返回 200。这里没有绕过验证码：复现假定用户已经完成合法邮箱验证。该权限是平台业务管理员，不代表自动取得 Django `/admin/` 的 staff 登录资格。

修复：公开注册仅允许 student/teacher（或固定 student），拒绝其他值；管理员创建必须走受保护的管理流程。验收至少覆盖管理员角色拒绝、未审核教师拒绝、教师跨课程编辑拒绝。

### R2 · P1：头像上传可保存 HTML，存在同源脚本执行风险

位置：`accounts/views.py:222-236`；`ts_courser/utils.py` 的 `compress_image()`。

只检查客户端声明的 `content_type`。小于 1 MB 的文件会原样保存；直接给模型 ImageField 赋值也不会自动执行表单图片验证。

复现：普通学生上传文件名 `probe.html`、声明 `image/png`、实际内容为 HTML，接口返回 302 并保存为 `avatars/probe.html`。若部署按扩展名以同源 `text/html` 提供该文件，访问链接即可运行上传者脚本。已验证存储绕过，未在生产浏览器执行脚本。

修复：用 Pillow 实际解码并重新编码允许的栅格格式，服务端确定扩展名，限制像素数和大小；失败必须拒绝。对 Vditor 和课程缩略图采用相同规则。Vditor 当前 `image/*` 允许 SVG，缩略图也没有严格解码校验。媒体可另放无应用会话的独立来源。

### R3 · P1：仓库默认配置不能作为生产配置使用

位置：`ts_courser/settings.py:25-30`。

SECRET_KEY 写死在仓库、DEBUG=True、ALLOWED_HOSTS 为空。部署检查还报告 HTTPS 重定向、HSTS、Session/CSRF secure cookie 未配置，共 7 项警告。直接换公网域名运行会遇到 Host 校验问题；简单放宽 Host 也不能解决其余风险。

修复：提供明确的生产 settings/环境变量入口，使用新的私密随机密钥，DEBUG=False，配置实际域名、HTTPS 和 secure cookie；反向代理信任配置必须匹配真实架构，HSTS 在 HTTPS 验证完成后启用。部署前使用实际生产配置重跑检查，记录由代理承担的配置项。当前未见生产部署配置，不能断言服务器端没有另行配置。

### R4 · P1：合法 JSON 的错误结构可使教师代码批改页崩溃

位置：`progress/views.py:425-438`；`teacher/views.py:909-916`。

提交端只验证 JSON 可解析，批改端直接假定是字典列表并调用每项的 `.get()`。

复现：已报名学生向代码提交接口传 `test_results=[1]`，返回 success；教师打开对应批改页返回 500。`null` 等结构也没有可靠边界保护。影响该份提交的审阅，默认选中它时也会使默认批改页崩溃，不是全站所有页面不可用。

修复：服务端校验列表、每项结构、字段类型、条目数和长度，错误返回 400；展示端兼容已经存在的坏数据。验收覆盖 `[1]`、`null`、对象、合法列表。

### R5 · P1（开放注册时）：邮箱验证码实际上未发送

位置：`accounts/views.py:24-52`。

接口只把验证码打印到服务器终端，却向用户返回发送成功。真实用户无法在自己的邮箱完成注册。这是文档已说明、上线时必须结束的 MVP 状态。

修复：完成真实邮件或学校身份登录；若首发统一分发账号，则关闭公开注册入口及接口，明确账号发放和恢复流程。验证码应采用安全随机源、尝试次数/发送频率限制，并停止写入明文日志。

## 业务正确性与其他安全发现

### R6 · P2：开放模式课程关闭报名后仍可通过学习页加入

位置：`courses/views.py:137-139`。

自动报名只检查 `enrollment_mode == 'open'`，没有检查 `enrollment_open`。复现：开放模式且 enrollment_open=False 的已发布课程，未报名学生直接 GET 学习页返回 200，并新增报名记录。邀请码模式的关闭课程不走这条路径。

修复：学习页自动报名与 `/api/enroll/` 共用报名规则。验收覆盖 open/code × 开放/关闭 × 已报名/未报名，不应阻止已有学生继续学习。

### R7 · P2：测验在发布结果前已将正确答案发送给学生

位置：`templates/courses/episodes/_tabs_quiz.html:40`；`templates/courses/learning_interface.html:456`。

学生作答时收到完整 quiz markdown，内含 `>+`、`>*`、排序位置及 FRQ 参考答案。`json_script`/`escapejs` 解决编码问题，不提供保密性。

复现：manual 发布策略、尚未提交的测验，其学习页 HTML 已包含测试用的正确答案标记内容。隐藏结果界面无法阻止查看源代码。

修复：若“发布”必须控制答案可见性，服务端解析题目并只下发去答案的作答结构，发布后按权限另行返回答案/评分。若仅做开放答案练习，应明确告知教师这个边界，不将其用于保密测验。

### R8 · P2：必答规则仅对 CBA 在服务端完整执行

位置：`progress/views.py:277-332`。

普通题型只检查题数和 type，没有统一检查必答内容、选择范围及完整性。复现：quiz_require_all=True 的单选题提交 `{"questions":[{"type":"mcq"}]}`，返回 success 并标记已读。

修复：为 MCQ/MRQ/SRT/FRQ/CBA 都定义服务端结构及完整性校验；必答失败不得创建提交或完成记录。

### R9 · P2：重交测验后新答案沿用旧 FRQ 评分

位置：`progress/views.py:355-365`。

update_or_create 更新 answers，但不清空 frq_grades；同时保留之前的 released_at。复现：已评分为正确的 FRQ 改写答案后重交，旧 `{"0":true}` 和发布时间均保留。教师审阅新答案时仍会显示旧评分，且新内容已经处于发布状态。

文档明确规定人工发布状态可以保留，但旧评分属于旧答案，不能因此一起复用。

修复：拒绝不可重交状态，或为每次提交建版本；允许覆盖时，至少使变化题目的人工评分失效，并明确是否需要重新审核。保留发布时间与保留评分应分别定义。

### R10 · P2：注册没有执行配置中的密码校验器

位置：`accounts/views.py:97-108`。

create_user 不会自动调用 AUTH_PASSWORD_VALIDATORS。复现：有效验证码条件下，密码 `1` 被接受并可校验成功。

修复：使用合适的注册 Form 或显式执行 validate_password，并校验用户名、邮箱等字段。为登录、验证码请求和验证码尝试增加限流；当前代码中未见这些保护。

### R11 · P2：登录后的 next 支持站外重定向

位置：`accounts/views.py:150-152`。

复现：有效登录请求使用 `?next=https://example.org`，返回 302 到该站外地址。可用于借可信登录流程引导用户进入钓鱼页面，不等同于直接窃取密码。

修复：用 Django 的 url_has_allowed_host_and_scheme 校验允许的 Host 和 scheme，不合法时使用默认课程页。

### R12 · P2：新建章节和课时的排序值从第二项开始重复

位置：`teacher/views.py:147,180`。

代码 `(max_order or -1) + 1` 把合法的 0 当成空值：空列表首项得到 0，第二项仍得到 0，此后自动新增可持续得到 0。会使按 order 排列的课程顺序与“追加到末尾”的预期不一致。

修复：仅当 max_order is None 时使用 -1；按需要加确定性的次级排序。该项为静态代码确认，未做单独 HTTP 复现。

3. **在实际 HTTPS 预发布域名验收完整流程。** 注册/分发账号 → 登录 → 报名 → 打开 PDF → 答题 → Python input → Stop → 再运行 → 提交 → 教师批改/发布 → 学生查看。检查生产 `.mjs`/WASM MIME、静态缓存及 COOP/COEP；wsgi.py 的 StaticFilesHandler 补丁只针对开发静态服务，不能替代生产代理配置。
4. **做一次备份恢复和回滚演练。** 备份数据库及 media，验证能恢复课程、账号、代码和测验提交。SQLite 采用一致性备份方法；上线期间保留上一个可部署版本与迁移回退策略。
5. **添加错误可见性。** 至少能发现 5xx、上传失败、静态资源失败和 Python 环境初始化失败；日志避免收集密码、验证码和不必要的学生答案。给学生明确的提交成功/失败状态，避免失败时误以为已交作业。

### 首发质量提升，优先于增加新功能

- **统一权限与提交规则。** 将报名/访问判断和测验解析/校验从多个 view 提取成共享服务；明确教师能否查看其他教师的课程内容。现有文档允许教师绕过报名，所以这里是政策选择，不是已证实的越权缺陷。
- **减少“我的课程”查询量。** progress/views.py 的 my_courses 对每个 episode 单独执行已读 exists；改为批量聚合。先用实际班级规模压测，再决定是否迁移 PostgreSQL，避免在上线前做未经验证的大规模数据库改造。
- **改善代码草稿与提交语义。** upload_code 会把唯一记录标记为未提交并覆盖内容；README/模型对此已有说明。若产品希望“已交作业仍保留，继续修改是草稿”，应分开保存草稿和正式提交，并支持历史版本。这属于产品改进，不将现有明确语义误报为新回归。
- **明确浏览器判题的用途。** README 已说明结果由浏览器自报，可用于课堂即时反馈；教师界面应标明其未经服务端验证。若用于正式评分，再引入隔离运行环境和服务端判题，不建议直接在 Django 进程执行学生代码。
- **统一 Markdown 清洗。** README 已假定教师可信，普通 Markdown 的 marked.parse 仍会保留危险 HTML；外部内容导入或扩大教师范围前，所有渲染入口都应使用统一清洗器，而非只保护部分题型。
- **确认媒体访问政策。** 课程页面的报名权限不会自动作用于静态媒体 URL。若课件要求私有访问，提供授权下载或短期签名访问；若本来就是可分享材料，则不必增加复杂度。
- **验证学校网络中的首屏体验。** 项目使用外部 CDN 和较大的 Python 运行时，实际教室网络下测冷启动；必要时自托管固定版本资源，保留加载进度、失败重试和保存中的明确状态。
